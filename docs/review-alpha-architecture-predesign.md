## Verdict: GO_WITH_CONDITIONS

No BLOCKER was filed. 18 MAJOR findings were confirmed against the design as written. The rescue pass named a specific design-text change for each one (17 dissolved, 1 partial; see Rescue pass). Three further problems surfaced as hidden blockers; each has a named change, so none forces NO_GO. The design is not GO because MAJOR findings are confirmed.

In plain words: the architecture (write-once vault files, one agent, a plain mirror folder, no driver) fits the owner's goal. The weak spots are all in the same few places. (1) The mirror planning table is not complete, so a partial or rolled-back vault view can overwrite or delete a user's newer file. (2) Everyday noise (junk files, temp files, conflict copies) is not handled, which breaks "just works". (3) Key replacement and lost-device handling leave gaps. (4) A dead or stale agent looks healthy. (5) The recovery-key file can land in a synced folder. All of these are fixable in the design text before any code. 15 numbered conditions follow.

## Must-fix-before-code conditions

Each is a change to `design-alpha-architecture.md`. Finding ids are in brackets.

1. **Make the 7.2 plan function total, and stop planning on an incomplete vault view.** Enumerate every cell of (mirror state x base state x head state) with an action. Add rows for "base exists but is absent from the merged graph", "head is an older ancestor of base", "mirror matches base, no head" and "mirror edited, head deleted (edit survives, per 7.1)". Rule: rows 2, 3, 7 and 8 apply only if the head descends from the base through records that are present; otherwise the node is "incomplete view" (no mirror write, no delete, status "waiting for provider"). Local state keeps the set of merged segment names; while any is missing, planning is report-only for all nodes. Add a vault-folder sentinel (vault id plus highest sequence seen per device tag). Add a property test that fails on any matrix cell without an action, and scenarios "half-delivered restore" and "sync client drops a seen segment". Note: M8 garbage collection and checkpoints legitimately remove segments, so the seen-set rule needs an exception written when M8 is designed. [durability-usability/vault-side-partial-view-rolls-files-back, integration-security/segment-loss-reverts-mirror-files, failure-migration/plan-table-has-no-row-for-base-without-head]
2. **Define the local mirror state and the folder and rename rules.** State schema: path -> (node id, base version id, size, mtime, file id, chunk-id digest). A folder removal applies only when the folder is empty after its children's rows run; otherwise the folder stays and a live or uncommitted child wins over the delete. File-id rename detection is part of the plan, not an option, and paired renames do not count toward the mass-delete guard. When stat is equal but the vault head differs, compare content (chunk ids) before any overwrite or removal. [hidden blocker HB-1; durability-usability/idle-poll-duty-cycle-and-mass-delete-friction for the guard counting]
3. **Specify conflict resolution as plan rows.** Mirror state keyed by path (condition 2), so each rendered conflict copy has its own base. Rows: delete the conflict copy = `discard` that head; delete the plain-name file while another head is live = `discard` the head at that path, survivor is renamed to the plain name by a checked internal rename; rename or move a conflict copy = `discard` plus a new node; edit a conflict copy in place = new version with base [that head]. Conflict-copy names are fixed at first materialization and not renamed by later edits; amend claim C4 to say names may differ across devices, data does not. Add `cloudcrypt conflicts --keep <file>`. Table-test all four cases. [durability-usability/conflict-resolution-semantics-unspecified, integration-security/conflict-copy-reimport-and-resolution-gap]
4. **Fix the apply order and temp-file handling.** `plainout` writes temp files only inside a reserved folder at the mirror root (for example `.cloudcrypt-tmp/`, same volume so rename stays atomic); the poller never descends into reserved names; startup sweeps stale temps. Write the apply order: write temp and flush, re-check target, move old file to trash, rename into place, update local base and flush state, with a crash table per step. Add plan row "mirror content equals a current head, base older: adopt as base, no commit". After the trash move, compare the trashed file to base; if it differs, re-plan the node as edited so it commits as a conflict. Add scenarios for temp-file feedback and crash injection after each step. [durability-usability/mirror-temp-files-picked-up-as-user-files, failure-migration/mirror-temp-files-committed, failure-migration/trash-swallows-concurrent-edit, hidden blocker HB-3]
5. **Add the ignore set, skip report and file-kind table.** A fixed built-in ignore set applied at commit time only (agent temp folder and sentinel, `.DS_Store`, `Thumbs.db`, `desktop.ini`, Office `~$*` lock files, partial-download suffixes). Symlinks and special files refused with a named status entry; hard links read as plain files; extended attributes and resource forks not stored, stated as a residual. Everything skipped is listed by name in `status` with a reason. A per-file commit rate limit (at most one commit per file per 60 seconds [judgement]) and a "too busy" skip after 10 minutes without quiesce. Add a large-file warning and a vault size alert. The ignore set is an input to the plan function and is table-tested. One materialization sanitiser (control and bidi characters, separators, dot-dot, trailing dots and spaces, length limits) for file names and device labels, fuzzed. State the mode and umask for materialized files. [durability-usability/no-ignore-or-skip-policy-for-mirror, integration-security/no-ignore-or-exclusion-policy, integration-security/non-regular-files-in-the-mirror, integration-security/names-and-labels-control-characters]
6. **Place every plaintext-bearing file.** The recovery-key file is written only by `plainout` through the T5 placement check, which refuses the vault folder, the mirror, any detected sync root or an ancestor of one; the save dialog starts at a non-synced place; print or write-it-down is the default offer; the screen warns that clipboard history may keep a copy; add an SC row with a break-it-by note. The same rule covers the trash, local state, `status.json`, logs and restore destinations: per-machine non-roaming paths (macOS Application Support, Windows LOCALAPPDATA, Linux XDG state), file names not logged above debug level, log rotation and size cap, trash capped by age and size, a free-space floor and disk-full and provider-full states, and J8 "Remove CloudCrypt from this device" also purges trash, state and keychain items. J6 and 8.4 state that old key files still open with the old password or old recovery key. State the cost as "mirror plus vault plus history plus trash". State the sync-root claim as conditional on detection (C5). [purpose-focus/recovery-key-save-location, integration-security/recovery-key-saved-into-synced-folder, purpose-focus/plaintext-residue-outside-mirror, integration-security/plaintext-copies-outside-the-mirror, durability-usability/unbounded-local-growth-trash-logs-state, durability-usability/recovery-key-lifecycle-and-circular-storage, cost-honesty/logs-and-status-hold-names, cost-honesty/disk-cost-three-copies]
7. **Advance the key-file high-water mark only from authenticated key files, and give the user a way out.** Header numbers before authentication are never stored. Bind the key-check block's associated data to the SHA-256 of the exact header bytes. A higher keyGen the device cannot authenticate shows "Locked: new vault key, enter password" and is never recorded. Add `cloudcrypt doctor --accept-folder` (page button in M5): shows what the device last saw and what the folder shows, needs a typed confirmation and a fresh unlock, then resets anchors and the seen-segment set. Remove "--accept-rollback ceremony" from the moot list in section 10 (renamed, not dropped). In 7.5 say which states stop writes and which only warn. Scenario: planted forged key file. [integration-security/high-water-mark-poisoned-by-forged-header, failure-migration/planted-high-water-bricks-devices]
8. **Refresh lists `keys/` every cycle and Commit fails closed on a newer key.** On a higher keyGen the agent stops writing, shows "Locked: new vault key, enter password" and notifies. Commit's first step is Refresh, so an offline device returning also refuses. State in C8 that a short window before the next refresh remains. Scenario: device running (or asleep) across a key replacement. [durability-usability/key-folder-not-repolled-stale-generation-writes, failure-migration/running-agent-keeps-writing-old-key]
9. **Identify keys by id and settle write authority of a retired key.** Packs, segments and the history block carry a random key id (hash of the key check or 16 random bytes); the counter is display order only. Define the fork winner (highest fileGen, tie by hash) and chain the loser's key into the next key file's history block. For the lost device: EITHER add a must-understand `rekey` record carrying a cutoff map (highest sequence seen per device tag), and readers quarantine retired-generation segments above the cutoff or from unlisted tags; OR state plainly in J7 and C8 that a lost device keeps write authority over generation g until the sync account is cut. 10. **Make a dead, stale or blocked agent visible.** `status.json` gains `updatedAt`, `lastGoodSync`, `filesNotYetInVault`. CLI and page show "CloudCrypt is not running, files are not being protected" when `updatedAt` is stale (over 2 minutes [judgement]); `status` falls back to reading `status.json` when the socket is dead. Restart policy in the J1 registration (launchd KeepAlive, systemd Restart=on-failure, Windows logon task restart; all [recall] to verify). A minimal notifier in `platform/spawn` (osascript, notify-send, a toast; [recall]) pulled forward from M9 to M4, rate-limited, fired for action-needed states. A 15-minute check job that runs `cloudcrypt status --notify` while the agent is dead. Warn when the last good sync is older than 3 days [judgement]. Reword the top status to "Saved to your vault folder; your sync client carries it" and add states: agent not running, files not yet in vault, disk full, provider full, this device needs a newer CloudCrypt, key replaced elsewhere. J4's "zero steps" claim says a user who disables autostart gets no alert. Scenarios: kill the agent mid-commit and mid-apply. [durability-usability/no-notification-or-supervision-for-states-needing-action, failure-migration/agent-dies-silently, cost-honesty/agent-dead-no-liveness, failure-migration/up-to-date-means-saved-locally]
